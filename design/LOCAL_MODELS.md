# 本地模型要做什么

**状态：只是方案，没有实现。** 现在所有模型调用都走硅基流动，引导页和设置里都写明了。标“估算”的数字没有实测。

## 先改哪个

三类模型看到的内容差别很大：

| 模型 | 用来做什么 | 发出去的内容 | 现在的用量 |
|---|---|---|---|
| 嵌入 `bge-m3` | 入库、每次提问 | **整个资料库的每个片段**和文件名 | 一次性全部发送 |
| 精排 `bge-reranker-v2-m3` | 每次提问 | 40～80 个候选片段 | 随提问 |
| 问答模型 | 规划、回答、核对 | 问题和选中的片段 | 随提问 |

所以顺序应该是**先本地化嵌入和精排，再本地化问答**。只换问答模型（最容易想到的 Ollama 方案）解决不了隐私问题：全部文档还是要发出去做向量。而只换前两个之后，发出去的就只剩被问到的那几段。

## 代码里要动的地方

模型调用集中在 `services/model_clients.py`，边界比较干净：

- `SiliconFlowEmbeddings`、`SiliconFlowReranker`、`build_chat_model` 三个入口，检索和入库只依赖它们的方法。
- 现在只有一个 `siliconflow_base_url` 和一个 Key。要改成每类模型各有提供方：`embedding_provider`、`rerank_provider`、`llm_provider`。
- `require_api_key()` 在 `RAGSystem.initialize` 里是硬性前提，没有 Key 文件库都不启动。全本地时要跳过。
- 检索阈值（`rerank_min_score` 等）是按 API 版的分数调的。用同一个模型的本地版，分数应该接近，但要重跑评测确认。

## 嵌入和精排：放进进程内

用 ONNX Runtime。它已经是本机 OCR 组件的依赖，下载机制也现成（`ingestion/ocr_runtime.py`：按需下载、固定版本和 sha256、下载一次），可以照搬。

| 项目 | 内容 |
|---|---|
| 模型 | `bge-m3`（约 1.2～2.3 GB，看量化程度）、`bge-reranker-v2-m3`（约 1.1 GB） |
| 安装包 | 不内置。保持 50 MB，用户选本地时再下载 |
| 分词 | 要加 `tokenizers`，约 10 MB |
| 速度（估算，CPU） | 嵌入每秒 10～30 个片段；1000 个文件约 3 万片段，**首次入库 20～50 分钟**。精排 40 条约 3～8 秒，现在 API 约 1～2 秒 |
| 内存（估算） | 峰值 2～3 GB |
| 后台优先级 | 沿用入库线程的低优先级，否则会拖慢回答 |

**切换模型必须重新生成全部向量。** 不同实现的向量不能混用，哪怕是同名模型。要在 `store_meta` 里记下向量来自哪个模型，切换时提示并重新入库（`data_safety.rebuild` 的流程可以复用，文件列表不丢）。

不做精排也是一个选项，`retriever` 本来就能退回 RRF 顺序，但代价很大：在 benchmark_v1 上，只融合时 Recall@5 是 78.6%，加精排后是 97.5%。

## 问答模型：Ollama

Ollama 提供 OpenAI 兼容接口，`build_chat_model` 改 `base_url` 就能连上，代码改动小，难在别的地方：

- **Ollama 要用户自己装**，还有自己的后台服务。引导里要检测它是否在运行、模型是否已下载。不把它打进安装包（体积、更新、许可都麻烦）。
- **依赖结构化输出。** 规划和核对要求模型返回 JSON（`QueryPlan`、`FaithfulnessCheck`）。小模型经常格式不对，要测失败率，必要时重试或降级。
- **速度（估算）。** 现在每题约 3400 token 输入、800 token 输出，加规划和核对。CPU 上每秒 5～15 token，**一题 2～5 分钟**；8 GB 显存的显卡约 30～60 秒。
- **质量要重新评测。** `answer_speed_v1` 里 Qwen3-8B 评分 4.75，30B 是 4.90。本地量化版可能更低，要跑同一套 20 题。
- 硬件门槛：8B 级模型约需 8 GB 内存或显存，30B 级约需 24 GB。很多办公电脑跑不动，所以云端选项要保留。

## 界面和文案

- 设置里加“模型放在哪里”，分别显示每类模型是本地还是云端。
- **数据去向要按实际配置说。** 现在的文案写死在 `guide.js` 的 `NOTICE` 和设置页，要改成根据配置生成。比如“文档文字留在本机，问题和相关片段发到硅基流动”。这部分不能含糊。
- 全本地时，引导跳过 Key 那一步。
- “云端识别图片”和“用 AI 写推荐问题”仍然会外发，要单独提示或在全本地模式下关闭。

## 工作量（估算）

| 阶段 | 内容 | 工作量 |
|---|---|---|
| 1 | 提供方配置、向量来源标记、切换时重新入库 | 2～3 天 |
| 2 | ONNX 嵌入和精排、组件下载、后台优先级 | 3～5 天 |
| 3 | 三个评测集重跑，校准阈值，对比准确率和耗时 | 1～2 天（本身要跑几小时） |
| 4 | Ollama 连接、检测、结构化输出容错 | 2～3 天 |
| 5 | 文案、引导、设置页、打包体积 | 1～2 天 |

只做 1～3 和 5 就能做到“文档不整体外发”，约 1.5～2 周。
