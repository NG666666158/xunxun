# 数据安全

实现在 `project/core/data_safety.py`，界面在设置 › 关于 › 数据安全（`ui/static/safety.js`）。

## 要保护什么

`knowledge.sqlite3` 里有文件表、片段、向量和推荐问题。其中**文件表没有别的来源**：哪些文件夹被监控、单个文件在哪、图片用什么方式读。片段和向量可以重新生成，只是要花时间和 API 调用。

`conversations.sqlite3` 里是对话记录和 Agent 状态（[设计](CONVERSATIONS.md)），只有这一份，也没有别的来源。它和索引库一起备份，但恢复时分开对待，见下面“对话记录”。

`parsed/`、`parents/` 可以由重新入库生成，`summaries/`（全文总结的笔记）可以重新读，都不备份。

## 启动检查

`DataSafety.prepare()` 在任何连接打开之前跑 `PRAGMA quick_check(1)`：

- 用 `quick_check` 而不是 `integrity_check`：它查页结构，不比对索引内容，快得多。48 MB 的库 85 ms，412 MB（1100 个文件）778 ms。
- 被锁住或打不开不算损坏。只有 SQLite 明确说文件坏了才算，否则一次偶发的占用会吓到用户。
- 损坏时不打开数据库。`RAGSystem.initialize` 抛 `DatabaseDamaged`，文件库相关接口返回 503，但 `/settings` 和 `/data-safety` 照常回答，界面才能给出恢复入口。
- 运行中查询遇到“malformed”，`ErrorDetailMiddleware` 也会走同一条路。

检查在后台线程里跑，不阻塞 `/health/live`，外壳的启动超时不受影响。

## 备份

`backups/<时间>/` 下每次一份，带 `manifest.json`，保留最近 3 份（`backup_keep`）：

- **时机**：启动 10 分钟后，之后每 24 小时。升级后第一次启动时，在打开数据库之前也备份一份，因为表结构迁移在打开时运行。也可以手动。
- **方法**：SQLite 备份 API，一步复制全部页（412 MB 用 5 秒）。WAL 模式下它只持有读快照，不阻塞写入；分多步复制的话，每次有写入就要从头开始，入库期间可能永远做不完。
- **校验**：复制完先跑 `quick_check`，通过了才改名成正式目录。没有 manifest 的目录不算备份。
- **副作用**：副本校验失败，说明正在用的文件坏了。所以每天的备份也是一次运行中的检查。
- **磁盘**：可用空间不到 1.5 倍时跳过，并在界面上说明。

## 两条恢复路径

都要替换文件，必须没有打开的连接。启动时检查失败的情况下，数据库从未被打开，当场就能做。如果已经在用，就写入 `recovery-pending.json`，下次启动时、打开数据库之前执行，外壳可以立即重启（`restart_app`）。待执行的记录先删除再执行，这样一次失败的恢复不会让程序永远起不来。

**从备份恢复**：索引库回到那个时间点。启动对账会重新读之后改过的文件，所以通常很快。先把备份复制到旁边再替换，磁盘满了也不会把现状弄坏。对话记录不跟着回去，否则备份之后的对话就丢了，只有它自己也损坏时才会替换。

**重新读一遍所有文件**：新建一个空索引，把文件表放回去，全部标为待读。文件表从损坏的文件里尽量读：表扫描遇到坏页会停，所以从两头各读一次，只丢坏页上的行；再用最新的可读备份补齐。墓碑行（已删除）保留。推荐问题表不保留，之后会重新生成。这条路要重新调用嵌入接口，所以确认框里写明了。

被替换的文件放在 `backups/replaced/`，只留最后一次的，第一次恢复选错了还能找回。

## 对话记录

索引库损坏时，`/conversations` 照常回答，侧栏还能看历史。对话库的连接也要等 `prepare()` 跑完才打开，这样待执行的恢复总在它之前。

对话库自己损坏时，两条恢复路径都帮不上忙：重新读文件变不出对话，索引回滚也和它无关。所以它不算“索引库已损坏”，不拦文件库和问答。启动检查发现后直接处理（`_heal_extras`）：

1. 损坏的文件放到 `backups/replaced/`。
2. 换成最新的、能通过检查的备份副本。没有副本就从空白开始。
3. 在设置 › 关于 › 数据安全里写明换成了哪个时间的备份，之后的对话没有保留。

运行中才发现的（每天的备份校验失败，或查询报“malformed”）只提示，等下次启动再处理，这时文件还开着，没法替换。查询的报错不说是哪个文件，所以先查一遍：索引库通过、对话库不通过，才算对话库的问题。

## 诊断导出

`core/diagnostics.py`：日志和一份摘要的 zip。不信任日志是干净的，因为异常信息可能引用模型的回复，也就可能引用文档。所以每行过白名单：

- 日志标题行保留，隐去 Key 和令牌（模式匹配加当前 Key 的字面值），用户目录替换成 `%USERPROFILE%`，隐去 30 字以上的连续中文和 `input_value=` 之类的引用内容，超过 240 字符截断。
- 调用栈只留文件和行号，异常只留类型，其余丢弃并记下丢了几行。
- 文件名会保留，这对排查有用，确认文字里写明了“可能含文件名”。

用真实日志试过：1934 行留下 1932 行，原始日志里 2 处长文本被去掉。
