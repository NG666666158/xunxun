# 对话存储

对话记录和 Agent 状态都放在数据目录的 `conversations.sqlite3`。实现在 `project/core/conversations.py`（后端）和 `project/ui/static/convstore.js`（前端）。

## 为什么单独一个文件

入库时 `knowledge.sqlite3` 写入很频繁，分开后聊天不用等入库。重建索引也不会碰到对话。备份时它和索引库一起，恢复时分开对待，见[数据安全](DATA_SAFETY.md#对话记录)。

## 两张“表”

- **`conversations`**：侧栏的历史记录。一段对话一行，消息是界面自己的 JSON，每次整段写入。列表接口不带消息，打开时才读，所以没有数量上限也不会拖慢启动。
- **`checkpoints` / `writes`**：LangGraph 的状态，由 `langgraph-checkpoint-sqlite` 管理。

## 状态的取舍

- **每段对话只留最新一个 checkpoint。** 每个 checkpoint 都存完整状态，而产品不需要回到过去的状态。全留的话，每轮要多存约 8 份，每份 50～100 KB。
- **一轮结束时才写（`durability="exit"`）。** 进程中途被杀时，这一轮不会进入上下文，下一个问题接在上一轮完整的回答之后。
- **删除时记下已删除的 id。** 回答还在跑时删除对话，这次运行之后的写入都丢弃，状态不会复活。这份记录只在内存里，因为重启后不会有还在跑的回答。
- **新一轮提问才解除这个标记。** 追问建议只读状态，不解除。
- **依赖版本。** 用 3.1.1：它要求 `langgraph-checkpoint>=4.1.0`，和锁文件一致，不用连带升级。

## 比状态更早的对话

迁移来的对话只有文字。第一次用到时，`state_from_text` 从文字重建状态：

- 问答对，让追问知道“它”指什么。
- 最后一轮的问题、回答和引用（引用的摘录充当段落），让追问建议能用。

演示工具的回答不算在内，它们不是知识。

## 从 localStorage 迁移

启动时 `moveLegacy` 把旧数据发到 `POST /conversations/import`：

1. 同一个事务写入，已有的 id 不覆盖，所以重发是安全的。
2. 接口返回所有已存的 id。每段都确认存在，才写“已迁移”标记并删除本地副本。
3. 失败或缺了任何一段，本地副本原样保留，下次启动再试。读不出来的数据也原样保留。

## 保存

`Saver` 按对话排队：

- 同一段对话一次只发一个请求，内容以最新的为准。
- 不同对话互不等待，所以几段可以同时流式回答。
- 失败后一直重试，期间侧栏显示提示。
- 删除排在正在进行的保存之后，之后的保存也不会把它带回来。
- 问题发出时立刻保存一次，回答结束再保存一次。

没有做“本地更新时间比较”：系统时钟回拨时，它反而会拒绝新内容、造成丢失。桌面版只有一个主窗口写对话。
