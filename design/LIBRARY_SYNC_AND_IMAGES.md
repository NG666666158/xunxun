# 单个文件、图片识别与文件库自动同步

状态：两个阶段都已实现（2026-10-28）：第一阶段是后端与 API，第二阶段是界面，见第 5 节。

## 0. 目标

用户原话的两件事：

1. 除了文件夹，也能添加**单个文件**；添加的是图片时，问一次用本地 OCR 还是多模态模型识别内容。
2. 资料库只记录文件路径；电脑上的文件夹改名、移动，文件增加、减少时，软件里**自动跟上**。

原则：

- 原文件永远不复制、不改动（浏览器上传除外，它拿不到路径）。
- 移动、改名不重新向量化；内容没变就不重新解析。
- 改了一段只重算这一段附近的向量。
- 回答问题时，后台索引让路。

## 1. 添加文件与文件夹

### 1.1 流程

```
界面选中/拖入路径
  └─ POST /library/inspect   只看不登记：按类型计数、图片张数（含文件夹里的）、各方式的预计耗时和云端调用次数
       └─ 有图片且偏好为 ask ─► 界面问一次（显示张数与预计），可勾“记住我的选择”
  └─ POST /library/import    文件 → import_path（原地登记）；文件夹 → add_root（监控）
       └─ 立即登记 → 按名字、时间、文件夹立刻能找到（文件搜索包含 pending） → 后台队列读内容
```

### 1.2 图片文件

支持 `.png .jpg .jpeg .webp .bmp .tif .tiff`，解析器 `ingestion/images.py`，复用 `figures.py` 的读取器与按图片哈希的缓存：

| 方式 | 做什么 | 上传 |
|---|---|---|
| `local`（默认） | RapidOCR 识别图中文字；组件首次使用时下载 | 不上传 |
| `cloud` | 视觉模型（`vision_model`，默认 Qwen3-VL-32B）一次调用：一句话说明是什么图 + 原样转写全部文字 | **上传图片** |
| `name` | 只记文件名、所在文件夹、日期（EXIF 拍摄日期，没有则用修改时间） | 不上传 |

- 每种方式都写入“图片：名字 / 文件夹 / 日期”三行，没有文字的照片也能按名字、文件夹、日期找到。
- 读取前把长边缩到 `image_max_side`（2000 px）。JPEG 原图保持 JPEG（上传更小），其余转 PNG，透明背景铺白。PyMuPDF 解码 PNG/JPEG/BMP/TIFF；WebP 用 Pillow（随本地 OCR 组件下载）。多页 TIFF 每页一段，最多 20 页。
- 云端读取失败（超时、限流）会抛错，文件留在“失败”稍后重试，不会悄悄只按名字入库。
- 选了 `local` 但 OCR 组件还没下载：先按名字入库，`notice = "ocr_unavailable"`；组件就绪后，下一次巡检自动重读这些图片。
- 同一方式的图片任务并行：云端 `vision_concurrency`（6）路，本地 2 路，`name` 4 路。

### 1.3 记住选择

- 每个文件存自己的 `image_mode`（registry 迁移新增列）。之后改了文件再索引，沿用它的方式。也可以单独改：`POST /files/{id}/image-mode`。
- 文件夹也存 `image_mode`：以后出现在这个文件夹里的新图片用同样的方式。
- 全局偏好 `image_import_mode`：`ask | local | cloud | name`，存在 `preferences.json`。新图片取值的顺序：本次导入的选择 → 所在文件夹的 → 偏好（不是 ask 时）→ `local`。

### 1.4 扫描件 PDF

`image_understanding = off` 且文件自己没选过方式时：

- 一半以上页面没有文字层的 PDF，记 `notice = "scanned_pdf"`，界面可以问“这份 PDF 是扫描件，要识别文字吗？”。
- 完全没有文字层的扫描件，原来会失败；现在先按名字入库，能被找到。
- 用户选“识别”：`image-mode` 设为 `local` 或 `cloud`，只对这份 PDF 生效，覆盖全局设置，然后重读。
- 用户选“不用了”：设为 `off`，以后不再问。

## 2. 自动同步

### 2.1 找回文件靠什么

- `os.stat` 给每个文件和文件夹都带了卷序列号（`st_dev`）和 NTFS 文件 ID（`st_ino`）。改名、同卷移动、进回收站（就是移动到 `<盘>\$Recycle.Bin\<SID>\`）都不改变它们。
- 路径不见时，先用 `OpenFileById`（以卷根目录的句柄作提示）加 `GetFinalPathNameByHandleW` 找到它现在的位置，再决定是不是“找不到”。代码在 `library/winfs.py`，用 ctypes，不需要管理员权限。实测一次约 0.4 ms。
- 文件被彻底删除后，`OpenFileById` 返回错误 87，判为“已不存在”。
- 跨卷移动等于“复制 + 删除”，文件 ID 会变：
  - 在监控文件夹内，仍按“大小 + sha256”匹配；
  - 否则标为“找不到”，用“重新定位”处理。
- FAT/exFAT、网络盘上查不到文件 ID，退回原来的路径和内容匹配。
- 不用 USN 日志：它需要管理员权限。

### 2.2 各种变化怎么处理

| 变化 | 怎么发现 | 结果 |
|---|---|---|
| 监控文件夹改名、同卷移动 | 监控它的**父目录**（非递归），收到它的 moved / deleted 事件；或任何旧路径事件、启动对账、30 秒巡检 | 按文件夹自己的文件 ID 找到新位置。在一个事务里改写文件夹和其下全部文件的路径，不重新索引；在新位置重新监控，再补扫一遍 |
| 监控文件夹被移进另一个监控文件夹 | 同上 | 合并：文件归入外层文件夹，原记录删除 |
| 监控文件夹进回收站 | 父目录事件 / 巡检 | 文件夹和其下文件都是 `recycled`；还原后回到 `active`，不重新索引 |
| 监控文件夹里的文件增、删、改、移动 | 原有的递归监控（防抖 2 秒） | 路径不见时先按文件 ID 找 |
| 文件被移出所有监控文件夹（同卷） | 同上 | 跟过去，转为“单个文件”，索引保留 |
| 单个文件改名、移动、修改、删除 | 启动时；`POST /library/sync`（窗口重新获得焦点）；`POST /files/{id}/check`（显示或打开前）；每 3 分钟的 stat 巡检 | 移动了就跟过去；改了就重读，未变的块复用向量；不见了就是 `missing` |
| 进回收站 | 按文件 ID 找到的路径在 `$Recycle.Bin` 下 | `recycled`：索引保留，但不进回答、不进文件搜索，不从回收站读取；路径仍显示原位置 |
| 从回收站还原 | 监控事件、巡检、`check` | 回到原状态，内容没变就不重新索引 |
| 从回收站彻底删除 | 文件 ID 已不存在 | 从资料库移除（用户删了两次） |
| Word 式保存（原文件改名成临时名，再写新文件） | 监控到“受支持 → 不受支持”的改名 | 两个路径都等保存结束后再看。记录留在文档路径上，只重算改动的块 |

### 2.3 增量向量

- `IngestionPipeline.index_document` 先取这个文件已存的“文本哈希 → 向量”（`EmbeddedStore.vectors_by_text`），只对新出现的文本调用嵌入模型。
- 子块的 id 含父块编号，改了一段后后面的编号会变，所以按**文本**而不是按 id 复用。
- 文本里有“文件名 · 章节”前缀：改了文件名或章节标题，对应的块会重算。只改名不会触发重新索引，见上表。
- Milvus 没有这个查询，照旧全部重算。

### 2.4 回答问题时让路

- `RAGSystem.chat/stream` 在回答期间持有 `library.answering()`。
- 后台队列在两种时候等待回答结束：每个文件开始前，以及同一文件的两次嵌入请求之间。
- 单次最多等 `index_yield_max_seconds`（120 秒），不会被连续提问饿死。
- 状态里的 `paused` 为真时，界面可以显示“先回答你的问题”。

### 3.2 `POST /api/v1/library/import`（本机）

```json
{"paths": ["…"], "image_mode": "local" | "cloud" | "name" | null, "remember": false}
```

```json
{"results": [
   {"path": "D:\\资料", "kind": "folder", "ok": true, "already": false, "root": {"root_id": "…", "status": "active", "image_mode": "local", "…": "…"}},
   {"path": "C:\\…\\白板.jpg", "kind": "file", "ok": true, "already": false, "file": {"file_id": "…", "status": "pending", "image_mode": "local", "image": true, "…": "…"}},
   {"path": "C:\\…\\a.exe", "kind": "error", "ok": false, "error": "不支持的格式：.exe"}

```

- `remember: true` 同时把 `image_mode` 存为偏好。
- 已监控的文件夹再次加入时会重新扫描，返回 `already: true`。
- 不支持的单个文件不登记。
- 文件夹在后台扫描；进度看 `/library/status` 的 `scanning` 与 `batch`。

### 3.3 `GET /api/v1/library/status?since=<seq>`

在原有字段上增加：

```json
{
  "busy": true, "queued": 40, "running": 6, "paused": false, "progress": 0.42,
  "current": {"file_id": "…", "name": "流程.png", "path": "…", "started": 1761620000.1},
  "batch": {"done": 30, "failed": 0, "skipped": 2, "total": 78, "finished": 32},
  "counts": {"pending": 40, "indexed": 900, "missing": 2, "offline": 0, "recycled": 1, "…": 0},
  "lost": {"missing": 2, "offline": 0, "recycled": 1},
  "changes": {
    "seq": 57, "since": 50,
    "counts": {"new": 3, "moved": 1, "recycled": 1},
    "user": {"folder_added": 1},
    "items": [{"seq": 57, "kind": "new", "source": "auto", "at": 1761620001.2, "file_id": "…", "name": "a.md", "path": "…"}],
    "truncated": false
  },
  "roots": ["…"]

```

- `changes` 只在带 `since` 时返回。界面记住上次的 `seq`，下次带上。
- `counts` 只数软件自己发现的变化，可以直接做提示，例如“寻寻发现 3 个新文件，正在读”。用户自己添加的（`user`）不做提示。
- 种类：`new changed moved removed missing offline recycled restored folder_added folder_moved folder_missing folder_recycled folder_restored folder_removed`。
- 移动类条目带 `old_path`；文件夹条目带 `root_id` 和 `files`。
- 只保留最近 2000 条，更早的 `since` 返回 `truncated: true`。

### 3.4 其他

| 接口 | 用途 | 返回 |
|---|---|---|
| `POST /api/v1/library/sync`（本机） | 窗口重新获得焦点时调用：单个文件逐个 stat，丢失的按 ID 再找一遍，文件夹逐个核对；3 秒内重复调用返回上次结果（`cached: true`） | 各结果的计数、`elapsed_ms`、这次的 `changes` |
| `GET /api/v1/library/lost` | “找不到的文件”列表 | `{"files": [文件视图]}`，状态为 missing / offline / recycled |
| `POST /api/v1/files/{id}/check`（本机） | 显示或打开一个文件前先核对 | 文件视图（可能已变成 moved、recycled 等） |
| `POST /api/v1/files/{id}/image-mode` | `{"mode": "local"\|"cloud"\|"name"\|"off"}`：图片文件可选前三种；PDF 可选 local / cloud / off；其他格式返回 400 | 文件视图（需要重读的话是 pending） |
| `PUT /api/v1/settings` | `image_import_mode: ask\|local\|cloud\|name`；`GET` 也返回它 | 设置 |
| `POST /api/v1/documents` | 浏览器上传，表单可带 `image_mode` | 同前 |
| `GET /api/v1/files?status=missing,recycled` | 状态筛选支持 `recycled` | 同前 |

文件视图新增 `image_mode`、`notice`（`scanned_pdf` / `ocr_unavailable` / null）、`image`（是否图片文件），`status` 可能为 `recycled`。文件夹视图新增 `image_mode`，`status` 可能为 `recycled`。

### 3.5 状态

文件：`pending → indexing → indexed | failed | unsupported`；丢失时变为 `missing`（同卷可用、找不到）、`offline`（卷未接入）或 `recycled`（在回收站）。

可被检索、引用的是 `indexed`、`missing`、`offline`：它们的解析文本还在，原文件不可用时阅读器显示解析文本。`recycled` 的索引保留，但被隐藏（`LibraryService.hidden_ids` 接到 `HybridRetriever.hidden_documents`）。

文件夹：`active | missing | offline | recycled`。

## 4. 实测

测量环境：本机 Windows 11、NTFS（C 盘），代理上网访问硅基流动，2026-10-28。脚本和原始结果在 `evaluation/library_sync_v1/`：

- `measure_sync.py`：真实 watchdog，假的索引器；
- `measure_reindex.py`：真实 bge-m3 嵌入；
- `measure_images.py`：真实 RapidOCR 和 Qwen3-VL-32B；
- `e2e.py`：真实后台，跑在用户数据的副本上。

### 4.1 发现移动有多快

| 情形 | 结果 |
|---|---|
| 监控文件夹改名（1000 个文件，6 次） | 0.35–0.37 s，中位数 0.36 s。其中 0.3 s 是有意的等待，让移动稳定下来。真实后台经 API 观察为 0.38 s |
| 监控文件夹移到另一个父目录（3 次） | 0.35–0.37 s |
| 改写 1000 个文件的路径（一个事务） | 37 ms |
| 以上全部移动、进回收站、还原，重新索引的文件数 | **0** |
| 监控文件夹进回收站 / 还原 | 0.26 s / 0.32 s |
| 单个文件改名移动，靠 `/library/sync` 发现 | 一次 sync 检查 300 个单个文件 78–82 ms；真实后台 1 个文件 10 ms |
| 单个文件进回收站（真实回收站） | 下一次 sync 时发现，77 ms |
| 单个文件在窗口不获得焦点时 | 最迟等巡检周期 `library_sweep_seconds`（180 s）；打开或预览前调用 `check` 会立即发现 |
| 按文件 ID 查一次路径 | 约 0.4 ms |

### 4.2 改一段后重新索引（310 页 PDF，1014 个子块）

用的是用户资料里的《AI-Agents-in-Depth-zh-CN.pdf》的副本，改写第 156 页正文的一行。解析后有 2 个子块的文本变了：改动所在的块，以及与它重叠的下一块。文件名不变，跟原地编辑一样。

| | 嵌入的块 | 复用 | 嵌入请求 | 嵌入耗时 | 总耗时 |
|---|---|---|---|---|---|
| 之前（不复用，第 1 次） | 1014 | 0 | 32 | 47.3 s | 53.5 s |
| 之前（不复用，第 2 次） | 1014 | 0 | 32 | 119.1 s | 124.5 s |
| 之后（复用，第 1 次） | 2 | 1012 | 1 | 2.1 s | 8.8 s |
| 之后（复用，第 2 次） | 2 | 1012 | 1 | 2.1 s | 7.7 s |

- 之后的总耗时大部分是解析这份 PDF（约 6 s），不再取决于网络。
- 硅基流动的嵌入延迟波动很大：同样 32 个请求，一次 47 s，一次 119 s。首次全量索引的一轮里还遇到两次连接中断。

### 4.3 每张图片的识别耗时

6 张图都不是用户自己的：

- 设置截图、发票、季度图表、手机长截图，用程序生成；
- 一页书的扫描图，就是上面那本书的第 156 页；
- 一张 4000×3000 无字照片。

缩放（解码、长边缩到 2000 px）49–130 ms；4000×3000 的 JPEG 要 625 ms，1.69 MB 缩到 0.97 MB。

| 图片 | 本地 RapidOCR | 识别字数 | 云端 Qwen3-VL-32B | 识别字数 |
|---|---|---|---|---|
| 设置截图 1600×1000 | 3.0 s | 98 | 11.5 s | 142 |
| 季度图表 1400×900 | 2.6 s | 50 | 12.0 s | 84 |
| 发票 900×1500 | 3.8 s | 136 | 35.0 s | 277 |
| 手机长截图 1170×2532 | 6.6 s | 562 | 44.8 s | 651 |
| 书页扫描 2000 px | 10.7 s | 1233 | 40.0 s | 1449 |
| 无字照片 4000×3000 | 2.3 s | 0 | 14.4 s | 24（“图中无可见文字”） |
| **单张中位数** | **3.4 s** | | **24.7 s** | |
| 6 张并行（本地 2 路 / 云端 6 路） | 15.0 s，合 2.5 s/张 | | 77.4 s，合 12.9 s/张 | |

- 本地引擎首次加载 0.8 s。
- 云端多出来的是“这是一张……”的说明句，以及本地漏掉的小字。本地对清晰的文字截图已经够用。
- 云端并行只快了约 2 倍，服务端没有线性扩展。

`inspect` 的估算按这些数：

- 一张图的时间取单张中位数；
- 多张图取“张数 × 并行后每张的秒数”，两者取大；
- 文本（2026-11 起，`library/estimate.py`，实测见 `evaluation/import_speed_v1/REPORT.md`）：各环节同时进行，取最慢的一个，不再相加。嵌入受账户每分钟 token 上限约束（免费账户 bge-m3 约 50 万/分钟，开头有一次约 100 万的突发额度）；小文件多时受请求数约束（每次约 0.4 s，4 个文件同时读）；解析、分词和写库按单核计；图片和扫描页与文本同时识别。
- 原来按“每个文件 0.2 s + 每 32 块 1.5 s”逐项相加，9,347 个文件的文件夹估成 7.5 小时，比实际长得多。

### 4.4 端到端（真实后台 + 用户数据副本）

数据副本用 SQLite backup 从 `%APPDATA%\EnterpriseKnowledgeBase` 拷出，原目录只读不写。

- **启动对账**：123 个真实文件（106 已索引、11 失败、6 不支持）。没有误判移动、丢失，也没有重新索引；registry 迁移在真实库上一次通过。
- **inspect**：文件夹里有 1 张图，偏好为 `ask`，所以要问；各方式的估算是本地 3 s、云端 25 s（1 次调用）、仅文件名 1 s。
- **import**（选本地）：0.5 s 后在文件列表和文件搜索里都能按名字找到“白板照片.png”，状态是 indexing。5.8 s 后队列空闲，图中 5 行字全部入库。
- **提问**“会议白板上写的暗号是什么？负责人是谁？”：10.5 s 答对“蓝鲸七号 / 张工”，引用 白板照片.png。
- **单个文件移动**后调用 sync，10 ms 跟上。
- **文件夹改名** 0.38 s 跟上，文件全部 indexed，路径已更新。

端到端时发现并修好了两个问题：

1. **长路径**：图片识别缓存的路径（数据目录加约 75 个字符）超过 260 字符时写不进去。现在缓存加 `\\?\` 前缀。这个缓存 PDF 插图也在用。
2. **网络抖动**：一次嵌入请求断线，文件就停在“失败”，要等下次启动才重试。现在网络或模型服务类的失败按 15 s、30 s、1 分钟、2 分钟、4 分钟自动重试。

另外看到一个问题，没有改（不在本任务的文件范围内）：`services/model_clients.py` 的嵌入重试只捕获 `httpx` 异常，而 OpenAI SDK 把断线包装成 `openai.APIConnectionError`，所以单个请求从不重试。问答时的查询嵌入也受影响，会退回只用 BM25。

## 6. 并行入库

用户反馈：开了本地 OCR 之后，大 PDF 识别特别慢，后面的文件都要排队；还有 9 个文件失败，原因都是 “Connection error.”。

### 6.1 做了什么

- **几个文件同时读**（`library/jobs.py`）：
  - 4 个工作线程从同一个队列取文件，同一个文件不会被两个线程同时读。
  - 排队顺序：用户在等的文件最先，比如刚添加的、正在打开的、要求重新入库的；其余按预计耗时从短到长。
  - 文件分三类：`light` 不需要识别，`ocr` 是很快能识别完的图片或只有几页扫描的 PDF，`long` 是长扫描件。
  - 识别类文件最多同时 2 个，其中长扫描件最多 1 个。其他线程继续读文本类文件。
  - PDF 有几页扫描件，是抽样 12 页判断的，结果按文件版本缓存。
- **扫描件边读边可搜**：每读完 16 页就提交一次，后面再提交时只为新出现的块算向量。状态里有页数进度，界面显示“01 申报书.pdf 16 / 61 页”。
- **本机 OCR 更快**：
  - 多个识别引擎同时读不同的页：每个引擎 2 个线程，引擎数是（逻辑处理器数 − 2）÷ 2，本机 12 个逻辑处理器即 5 个。每个约 25–35 MB，用到时才创建。
  - 每个引擎用 2 个线程而不是 1 个：一张图片只有一页，1 个线程时单页要慢一倍左右。
  - OpenCV 限制为 1 个线程。
  - 页面渲染仍在一个线程里做，因为 PyMuPDF 不是线程安全的。
  - 照片在识别前先把长边缩到 2000 px，这个第一阶段就有。
- **不拖慢提问**：
  - 后台线程的优先级调低：库的工作线程低于正常，识别线程最低。两边都要处理器时，回答先用。
  - 回答期间不再开始新的一页、新的文件和新的嵌入请求，这个第一阶段就有。
  - 正在读的那几页无法中途停下，所以光靠暂停不够，还需要调低优先级。
- **连接中断会重试**（`services/model_clients.py`）：
  - 以前的重试只认 `httpx` 的异常，而 OpenAI SDK 把断线包装成 `openai.APIConnectionError`，所以一次断线就让整个文件失败。
  - 现在断线、超时、429、5xx 都会重试：入库最多 6 次，间隔 1→20 s，带抖动；提问最多 3 次，间隔不超过 4 s。Key 无效、请求本身有错不重试。
  - 视觉模型调用用同样的规则。以前它对任何错误都重试 4 次，包括内容被拒这类重试也没用的错误。
  - 后台的嵌入和视觉调用全局最多同时 4 个，多个文件并行时不会触发限流。提问的调用不占这个名额。
  - 测量时本地后台也出现过同一种断线：连接空闲后被对方关掉，再拿来复用就报错。重试一次就好。

新增设置：`index_workers=4`、`index_ocr_jobs=2`、`index_long_jobs=1`、`index_api_concurrency=4`。

### 6.2 实测

数据是用户资料的副本：

- 《02 精密级合金粉末宏量开发 / 01 申报书.pdf》，13.1 MB，61 页，全部是扫描页；
- 15 张图片：13 张 3–7 MB 的微信照片，加 2 张 png 和 2 张小 jpg。

都用本机 OCR。场景是添加这个文件夹；8 秒后往里放一个小 Markdown 文件。改动前后是同一台机器、同一个场景，各用新的数据目录。脚本在 `evaluation/library_sync_v1/`。

**单个扫描件的 OCR 速度**（24 页，页面渲染单独计时，每页 0.11 s）：

| 设置 | 页/秒 |
|---|---|
| 原来：1 个引擎，2 个线程共用，ONNX 默认线程数 | 0.283 |
| 1 个引擎，1 个线程 | 0.244 |
| 2 个引擎 × 6 线程 / 3 × 4 / 4 × 3 | 0.268 / 0.304 / 0.340 |
| **6 个引擎 × 2 线程（采用 5 × 2）** / 12 × 1 | **0.384** / 0.389 |
| 8 / 10 个单线程引擎，OpenCV 单线程 | 0.396 / 0.410 |

另外几项观察：

- 用进程代替线程没有更快（6 × 2：进程 0.488，线程 0.480）。瓶颈在计算，不在 GIL。
- 把页面缩到 1.5 倍，检测快约四分之一，但英文单词会粘在一起，比如 “Scanned2026”。所以仍用 2.0 倍。
- 时间主要花在逐行识别上，每页 1–3.7 s；文字检测约 0.8 s，方向判断可以忽略。

**整批入库**（`measure_parallel.py`，改动前后各用新的数据目录）。测量时这台电脑本身负载不同，分两组记录：

| | 改动前 | 改动后 |
|---|---|---|
| 小文件（第 8 秒放入）等多久入库 | 246.5 s | **7.1 s** |
| 15 张图片：一半完成 / 全部完成 | 236 s / 253 s | **95 s / 147 s** |
| 扫描件第一次能搜到 | 216 s（读完才能搜） | **64.8 s** |
| 扫描件读完 / 全部完成 | 216.5 s / 255 s | 185.7 s / 186 s |

上表是电脑较空闲时（改动后一列是 5 引擎 × 2 线程、尚未降低优先级的版本）。

| | 改动前 | 改动后 |
|---|---|---|
| 小文件等多久入库 | 1056 s | **11.9 s** |
| 图片一半完成 / 全部完成 | 1001 s / 1066 s | **324 s / 760 s** |
| 扫描件第一次能搜到 | 930 s | **292 s** |
| 全部完成 | 1068 s | 1009 s |

上表是同一时段、电脑上别的程序占着 60–70% CPU 时（壁纸程序、用户正在运行的寻寻等），改动后为最终版本。

- 别的程序也在用 CPU 时，识别线程优先级低，会让着它们，所以扫描件本身没有变快（0.065 → 0.06 页/秒）。
- 但排队的问题解决了：小文件和图片不再等扫描件读完，扫描件也边读边能搜。

**回答速度**（`measure_latency.py`）：

- 方法：同一个已入库的资料库，同一个问题。先空闲时问 3 次；再清掉识别缓存，让扫描件真的重新逐页识别，在识别期间再问 3 次。
- 比较两项：首个字出现的时间，以及整个回答完成的时间。

| 同一负载下 | 空闲时（完成） | 识别期间（完成） | 识别期间（首个字） |
|---|---|---|---|
| 改动前 | 27.3–35.9 s | 29.6 / 30.9 / 51.7 s | 11.3–24.6 s |
| 改动后 | 23.0–25.4 s | **22.5 / 26.4 / 39.0 s** | **8.6–16.0 s** |

- 中间试过的一版没有降低优先级：识别期间的回答比空闲时慢了约 5 s。
- 原因是回答期间虽然不再开始新的一页，但已经在识别的几页停不下来，一页满负载要约 11 s。
- 降低优先级后，这部分不再拖慢回答。

### 6.3 没做的

- 用进程隔离识别：测过和线程一样快，还多占内存。
- 降低渲染倍率：会把英文单词粘在一起。
- 云端视觉模型改成一批页面并行发出：已经受全局 4 个并发限制，没有再改。
