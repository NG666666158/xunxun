# 大库导入后的文档卡片（doc_cards_after_import）

2026-11-11，分支 `claude/doc-cards-lazy-v1`（基于 `claude/import-speed-v1` c272568，即 main 1.0.2 + 导入提速）。

起因：每个读完的文件要调一次 Qwen3-8B 写文档卡片，两次调用至少隔 3 秒，先进先出。9,347 个文件的文件夹导入后，还要在后台跑 12～13 小时，期间一直占着回答也要用的 Qwen 额度；“找一下我的简历”要等简历刚好排到才找得到。

## 结论

- **用户看的文件先做卡片。** 这是主要的改进。
  - 搜到的、打开的文件，以及类型问题最可能命中、却还没有卡片的文件，排到队首，导入进行中也照做。
  - 刚导入完、一张卡片都没有的 1,610 个文件的库里：问一次“找一下简历 / 合同 / 论文”，每题挪到队首 58～66 个文件，其中有 12～16/20 份简历、12/12 份合同、6/16 篇论文。
  - 按应用的节奏写完这些卡片再问一次（简历这一步 6 分钟；后两步各约 12 分钟，含上一步再问时挪上来的文件）：简历第 1 个就对、前 5 个都是简历，20 份里标出 13 份（6 种问法都一样）；合同 12/12 全部标出；论文标出 8/16，第 1 个仍是那篇被卡片标成论文的新闻。这个问题在 doc_cards_v1 里卡片写齐时也一样。
  - 旧的做法要等先进先出排到它们：这个库 2.1 小时才写完，9,347 个文件 12.5 小时；在那之前，每类文件找得到的比例只能随进度线性上升。
- **文件名已经说明类型的，不调模型。** 名字以类型词结尾的文件（“01 申报书.pdf”），排序时本来就以文件名为准，卡片改变不了它的类型。省下的调用占 3～5%（新闻标题式文件名）到 22%（用户实际的 123 个文件）。
- **按 token 控制节奏，有人提问后让路。**
  - 有人在用时，卡片每分钟最多用 9,000 token；每次提问之后 60 秒内不做（看着的文件除外）。
  - 10 分钟没人提问，放宽到每分钟 15,000 token，调用间隔从 3 秒缩到 1 秒。
  - 遇到限流照旧等 25～90 秒，并把速度减半。
  - 9,347 个文件（虚拟时钟，两版各自的代码）：没人提问时 12.5 小时降到 8.0 小时（22% 名字带类型时 6.6 小时）；每 5 分钟问一次时，旧版 12.6 小时、新版 13.7～16.8 小时。新版有意更慢：每分钟只用约 7,100 token，旧版约 10,000。
- **库页能看到进度。** 类型筛选在还没有任何类型时也显示，首项写“全部类型（N 个待判断）”，悬停写“还有 N 个文件在判断类型，约 X 小时”。对话里按类型找文件、而还有文件没判断时，回答末尾加一句“还有 N 个文件在判断类型，列表可能不全，稍后再问一次。”
- **几个文件合并成一次调用：测了，不用。**
  - 提示词里固定的说明约占一张卡片 810 token 里的 530，所以 4 个、8 个文件一起问，每个文件的 token 少 32%、39%。
  - 但 Qwen3-8B 判断类型的准确率从 0.891 降到 0.745、0.700：新闻被标成通知公告或报告的更多，论文从 15/16 降到 12～13/16。
  - 代码保留为开关 `doc_card_batch`，默认 1。
- **类型问题照样答对，没有回归。**
  - 公开库（110 个文件，卡片齐全）上的 32 道题和 doc_cards_v1 相同：只有类型的 14 题 命中@1 0.714、命中@3 1.000、类型@5 0.929、提到@5 0.36；带人名 / 公司名的 12 题 命中@1 0.917，带主题的 6 题 1.000，与 doc_cards_v1 完全相同
  - pytest、JS 测试和 `ci_tier.py check` 都通过；`ci_tier.py check` 结果不变（16 题，召回@5 1.000，MRR 1.000）。

## 一、改了什么

| 改动 | 位置 | 说明 |
|---|---|---|
| 优先队列 | `retrieval/doc_cards.py` `DocCardBuilder` | 堆，三档：ASKED（用户在看）→ NEW（单独加入的文件）→ BACKFILL（其余，按修改时间从新到旧）。同一文件只排一次，可以往前挪。 |
| 用户在看 | `FileSearchService._ask_for_cards`；`api/main.py` 的 `_looked_at` | 每次找文件，列出的文件 → ASKED。类型问题另外把搜索本身碰到的文件、加上“类型探测”的结果 → ASKED。阅读面板打开、“打开原文件”→ ASKED。 |
| 类型探测 | `FileSearchService._probe`、`doc_cards.type_probe` | 只在还没卡片、名字也不带类型的文件里搜文件条目：一次用类型词（“简历”），一次用类型的描述（“简历 履历 …：某一个人的履历：姓名、…”），各取 32 个，交替合并。后台线程做，不拖慢回答。 |
| 名字说明了类型就跳过 | `DocCardBuilder.sync/build_many`、`/library/types` | 不排队、不调用；“待判断”的数目里也不算它们。 |
| 按 token 控制节奏 | `DocCardBuilder.rate/_after_call/_wait_turn` | 下次调用的时间 = max(上次结束 + 间隔，上次开始 + 本次 token ÷ 预算)。预算：有人在用 9,000/分钟，10 分钟没人提问 15,000/分钟（这时间隔缩到 1/3）。提问时暂停。提问后 60 秒冷却，导入大批文件时也等，用户在看的文件这两样都不等。限流时预算跟着间隔减半。 |
| 最近一次提问 | `LibraryService.idle_seconds` | 冷却和“空闲”的判断依据。 |
| 进度 | `/api/v1/library/types` 增加 `seconds_left`；`app.js` | 筛选首项显示待判断数，悬停显示剩余时间。 |
| 回答里的提示 | `rag_agent/nodes.py` 加 3 行 | 搜索结果有 `untyped` 时，回答末尾加一句。 |
| 合并调用（默认关） | `CARD_BATCH_PROMPT`、`parse_cards`、`doc_card_batch` | 规则与单个文件的提示词逐字相同；输入哈希也相同，所以已有卡片不会重做。单文件提示词一字未改（有测试）。 |
| 读卡片更宽容 | `parse_card` | 模型偶尔写出没加引号的值（`"类型": 报告`），整行 JSON 读不出来；现在逐个字段读。 |

新设置（`config.py`，都可以写在 preferences 里覆盖）：`doc_card_batch=1`、`doc_card_tokens_per_minute=9000`、`doc_card_idle_tokens_per_minute=15000`、`doc_card_cool_down_seconds=60`。卡片提示词版本 `CARD_VERSION` 不变，已有卡片不会重做。

`rag_system.py` 只改了 2 行：构建器改传 `library=`，并把它交给 `file_search.cards`。`model_clients.py` 没有改。

## 二、测试方法（只用公开数据）

- **公开类型库**：沿用 doc_cards_v1 的 110 个文件，名字都是匿名的 `资料_0001.txt` 等：
  - 简历 20：ResumeNER 16 + resume_seven_class 4；
  - 合同 12：CUAD；
  - 论文 16：CSL；
  - 新闻 62：CRUD-RAG，其中 32 篇提到“简历 / 合同 / 协议 / 论文”。
  - 32 道题、清单和单文件卡片（2026-11-10 的提示词 v3，与本分支逐字相同）都来自 doc_cards_v1。
- **大库**：import_speed_v1 用真实 bge-m3 建好的 1,500 个合成文件（`small1500`，CRUD-RAG 新闻拼成，名字是新闻标题），复制一份，再用应用自己的导入把上面 110 个文件加进去。共 1,610 个文件，一张卡片都没有，相当于大批导入刚结束。
- **模型**：卡片用真实的 Qwen3-8B（关闭思考），检索用真实的 bge-m3 和 bge-reranker-v2-m3。回复按提示词缓存，重算不再调用。
  - 寻寻本身和测试共用一个账户，所以真实调用之间留了几分钟。节奏都用应用自己的设置，全程没有遇到限流：0 次。
- **节奏**：`pace.py` 在虚拟时钟上分别跑 main 和本分支的 `DocCardBuilder`。只替换时钟、模型和存储；每次调用 1.8 秒、810 token，是公开库上实测的单文件数字。
- **名字带类型的比例**：`name_doc_type` 对文件名计数。用户资料只用 SQLite 备份 API 读到内存里，只统计数目，不输出任何名字。

## 三、刚导入完时的类型问题（`big_library.py`，1,610 个文件）

问法和打分沿用 doc_cards_v1。每类先问一次，让应用自己的构建器把这次挪到队首的卡片写完，再问一次。下一类接着上一类已经写好的卡片做。卡片用真实的 Qwen3-8B，一次一个文件，每分钟 9,000 token。全程 0 次限流，`results/big_library_lazy_b1.json`。

| | 第一次问（还没有卡片，就是 main 此时的结果） | 写卡片 | 再问一次 |
|---|---|---|---|
| 找一下简历（20 份） | 第 1 个不是简历，只提到“简历”的新闻排在所有简历前面；前 5 个里 3 个是简历（靠重排）；按类型标出 0 份 | 64 张，6.1 分钟，55k token | **第 1 个是简历，前 5 个全是，标出 13/20**；另外 5 种问法都一样 |
| 找一下合同（12 份） | 第 1 个是合同；标出 1/12 | 120 张，12.5 分钟，109k token（含上一步再问时挪上来的 56 个） | **前 5 个全是合同，标出 12/12**；另外 3 种问法都一样 |
| 找一下论文（16 篇） | 前 5 个没有论文，其中 2 篇是只提到“论文”的新闻 | 114 张，12.1 分钟，108k token | 前 5 个里 2 篇论文，**标出 8/16**；第 1 个仍是被卡片标成论文的新闻 |

- **每再问一次，就再往下挖 64 个。** 第二次问时，探测在剩下没有卡片的文件里再取最像的 64 个，所以问得越多，覆盖越全；每次的代价有上限。
- **和 main 比。** main 按先进先出、每 4.8 秒一张来写。在这个 1,610 个文件的库里，6 分钟只写得完约 75 张随机的卡片，每类约 5%；要标出 65% 的简历，要等约 84 分钟。9,347 个文件的文件夹，要等约 8 小时。
  - 本分支挪到队首的数目只和问题有关，和库的大小无关。
  - 不过库越大，干扰越多，探测的命中率可能更低。这里只量了 1,610 个文件。
- **回答会说明。** 第一次问时，对话里的回答末尾会写“还有 1,541 个文件在判断类型，列表可能不全，稍后再问一次。”快速搜索窗口（`quick.js`）的接口也返回这个数（`untyped`），但窗口里还没显示。
- **耗时。** 搜索本身 p50 约 0.75 秒。第一次问时有一次 3 秒，是冷启动；探测在后台线程里做，不计入。

## 四、哪些文件先做：类型探测怎么搜（`big_library.py probe`）

在没有卡片的 1,541 个文件里（另有 69 个名字是“…新闻”，按名字就算新闻），只搜文件条目，看前 K 个里有多少个真是该类型的文件：

| 搜什么 | 简历（20 份）@32 / @64 | 合同（12 份）@32 / @64 | 论文（16 篇）@32 / @64 |
|---|---|---|---|
| 类型词（“简历”） | 12 / 19 | 11 / 11 | 0 / 4 |
| 类型描述（`type_probe`） | 2 / 6 | 6 / 10 | **6 / 7** |
| 同义词串 | 2 / 5 | 6 / 10 | 0 / 1 |
| 类型词 32 + 描述 32（采用） | **12** | **12** | **6** |
| 用正文段落代替文件条目 | 都更差（简历 6，论文 0～5） | | |

- 类型词找简历和合同最好，描述找论文最好，所以两个都搜，交替合并。
- 再加上问题本身的搜索碰到的文件，每题挪到队首 58～66 个文件，其中有：
  - 简历 12～16 份（问法不同）；
  - 合同 12 份，全部；
  - 论文 6 篇。
- 搜索本身还是一秒内返回（p50 约 0.75 秒），探测在后台线程里做。
- 论文是短板：只有标题、摘要和关键词的论文页，在一堆新闻里靠文件条目很难认出来。挪不到的那些只能等后台按顺序补。

## 五、节奏（`pace.py`，9,347 个文件，虚拟时钟）

| 用户 | 文件名带类型 | main | 本分支 | 本分支每分钟 token |
|---|---|---|---|---|
| 没人提问 | 4.6% | 12.5 h | **8.0 h** | 15,000 |
| 没人提问 | 22% | 12.5 h | **6.6 h** | 15,000 |
| 每 5 分钟问一次 | 4.6% | 12.6 h | 16.8 h | 7,100（main 10,000） |
| 每 5 分钟问一次 | 22% | 12.6 h | 13.7 h | 7,100 |

- main 的每张卡片 = 间隔 3 秒 + 调用 1.8 秒，每分钟 12.5 张、约 10,000 token。有人提问时，它只在回答的那几秒停下，回答一结束就接着发。
- 本分支：
  - 有人在用时，每分钟 9,000 token，每次提问后冷却 60 秒。这样连续的几个问题之间，卡片不和回答抢一分钟的额度。账户的 Qwen3-8B 额度低到一次严格模式的回答就可能用完，连续被拒后还会被限流好几个小时（见 doc_cards_v1、qwen3_8b_v1 的记录）。
  - 没人提问时，每分钟 15,000 token，约为 11-07 实测额度（约 3.5 万/分钟）的四成。剩下的足够用户回来时的第一个问题。
- 合并调用（第六节）可以再省三分之一的 token，但准确率代价太大，没有用。

- token 节奏实测：4 个一起那次，预算 9,000/分钟，实际 9,070/分钟，0 次限流。

## 九、没做的、后续

- **论文类型的探测弱**（6/16）。可以对“像学术摘要”的文件条目（有“摘要 / 关键词 / 研究”）另搜一次，或者把探测扩到 64 个。都要多花卡片调用，没有做。
- **第二次问才看得到。** 第一次问时卡片还没写，回答里只写了“稍后再问一次”。可以在卡片写完后自动刷新快速搜索的结果，要改 `quick.js` 和 `app.js`。另一个会话正在改 `app.js`，这里没动。
- **用户正在用时，补卡片比 main 更慢**（第五节）。这是有意的取舍。如果嫌慢，可以把 `doc_card_cool_down_seconds` 调小。
- **按回答里引用的文件挪到队首**：要改 `rag_system.py` 或 `nodes.py`，另一个会话正在改，没有做。
- **和重试会话（`feat/retry-v1`）的合并**：它在 `DocCardBuilder._ask` 的重试循环里加了 `chat_busy.wait(...)`；本分支把这个循环移到了 `_invoke`。合并时要把那一行放进 `_invoke` 的循环里。`nodes.py` 两边改的地方不相邻。
- 卡片的“对象 / 摘要”对名字带类型的文件不再生成。库页对这些文件只显示按文件名得到的类型。
